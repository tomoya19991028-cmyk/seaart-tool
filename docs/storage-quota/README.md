# 生成時の保存容量不足

生成ボタンは生成結果に加えて、その時点の入力設定を履歴へ保存する。
従来は保存途中の失敗やタブ間競合から復旧するため、変更前と変更後の
settings・working・historyを丸ごとJSON文字列で一時保存していた。
確定データに空きがあっても、この一時的な重複によってlocalStorageの上限に
達し、生成するたびに「ブラウザの保存容量が不足しています」と表示される。

復旧journalだけを、同梱したlz-string 1.5.0のUTF-16形式で圧縮する。
外部CDN・ネットワーク・追加の保存場所は使わない。元のJSON文字数と既存の
afHashによるチェックサムを検証してから、従来のjournal・bundle検証へ渡す。
圧縮が小さくならなければ従来形式をそのまま使う。

保存キーとnamespace、settings/working/historyの形式、バックアップJSON、
お気に入りと生成履歴の保存件数、保護された結果の利用条件は変更しない。
既存データや他の保存キーを削除しない。旧形式のjournalも読み込める。
破損や未知の形式は従来と同じく保存を止め、元データを保持する。

`npm run test:storage`では、新規・合成データだけで次を確認する。

- 実際のChromiumの容量上限まで他のキーを埋めた状態で、従来の書き込みが
  QuotaExceededErrorになる一方、圧縮版では連続7回の生成と再読み込みが成功する。
- Unicode（日本語・絵文字・結合文字・孤立サロゲート）の完全な復元。
- journal・3 payload・marker・journal確定の全6書き込みで、失敗時は元の
  保存状態へ戻り、再試行が成功する。
- 圧縮・従来journalの全6中断位置から、markerに一致する世代へ復旧する。
- 破損・未知の圧縮形式は保存済みのバイトを変えずに停止する。

既存の結果保護の容量試験は、256 KiBの確保に失敗したところで満杯と
見なしていた。圧縮版はその残り領域に正しく保存できるため、元ファイルと
全assertionを保持したまま、試験時の単一アンカー置換で確保単位を4 KiBへ
小さくする。十分な回数まで確保して、本当に新しいjournalが入らない状態で
保存拒否・RAM/ディスク/Undo/履歴の保持・空きを作った後の再試行を確認する。

本体データそのものや他サイトの保存で容量を使い切っている場合、圧縮だけで
必ず保存できるとは限らない。その場合も容量不足を表示し、設定や履歴を
自動削除しない。利用者の端末・既存の実データにはアクセスしていない。

同梱元：npm `lz-string@1.5.0` の`libs/lz-string.js`。
